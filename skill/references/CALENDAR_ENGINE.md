# 动态日期与日干支计算规则

## 原则

只要用户的问题涉及动态日期或某个具体日期，**大模型不得自行计算公历/农历转换或日干支**。

模型只负责两件事：

1. 读取程序已经算好的日期事实；
2. 基于这些事实做命理推理、解释和现实落点。

计算层与推理层必须分离。

## 事实引擎

动态日期使用：

- 项目：`6tail/lunar-python`
- 当前版本：`1.4.8`
- 许可证：MIT

典型程序调用：

```python
from lunar_python import Solar

lunar = Solar.fromYmd(1986, 5, 29).getLunar()
day_ganzhi = lunar.getDayInGanZhi()
```

`1986-05-29` 的公开 README 示例为 `癸酉日`，可作为回归测试基准。

## 什么时候必须先算

当前用户消息出现以下内容时，应先走日期解析器：

- 今天 / 今日；
- 昨天 / 昨日；
- 前天；
- 明天 / 明日；
- 后天；
- 明确公历日期，例如 `2026-09-14`、`2026年9月14日`；
- 明确农历日期，例如 `农历1986年4月21日`；
- 未写年份但明确写月日，例如 `9月14日`。

对于只写月日、没有年份的表达，当前实现按当前时区的参考年份解析，并把这个假设明确写进上下文。

## 时区

相对日期必须使用宿主系统明确的本地时区，不得直接用 UTC 解释“今天”。

“不求人”当前默认使用：

`Asia/Shanghai`

若宿主产品另有明确用户时区，应以宿主产品传入的时区为准。

## 模型禁止事项

模型不得：

- 心算某日是什么干支；
- 根据记忆猜日柱；
- 自己做公历转农历；
- 自己做农历转公历；
- 看到“今天”后按模型训练时的日期理解；
- 在程序没有返回某个日期结果时补一个看起来合理的干支；
- 把普通历法字段擅自扩写成未经程序计算的年柱、月柱、时柱。

## unresolved 处理

若日期表达无法被程序可靠解析，例如日期本身无效，或用户只说“那一天”却没有足够上下文：

- 标记为 `unresolved`；
- 告诉模型该日期尚未被可靠计算；
- 模型不得继续补算；
- 必要时要求用户给出明确日期。

## 和八字排盘的关系

这是两条不同的确定性计算链：

- **出生八字事实**：由经过验证的八字排盘引擎产生；
- **动态某日的日干支**：由 `6tail/lunar-python` 产生。

二者都属于事实计算层。

LLM 位于它们之后，只做解释，不做排盘。

## 一句话架构

> 程序负责把“哪一天、什么干支”算对；模型负责解释“这个干支碰到这个命局意味着什么”。
